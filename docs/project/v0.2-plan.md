# v0.2 plan

This is a plan, not a release promise. Each item becomes one or more pull requests with their own documentation, upgrade notes and evidence.
No version is tagged without the maintainer's explicit go-ahead; the [release checklist](./release-checklist.md) applies as it did for v0.1.

## Where v0.2 starts

v0.1 delivered M0–M4 ([milestones](./milestones.md)). Since `v0.1.0`, `main` has closed the findings of the 2026-10-21 review, and those
items are not repeated here:

- long inputs split instead of truncated (ADR-0009);
- deadlines and admission for model calls (ADR-0010);
- one index profile per database, with the anchor (ADR-0011);
- a time limit on retrieval SQL and on the wait for a connection.

The round of changes that this plan closes adds:

- the served text and every retrieval setting in the evaluation drift check (ADR-0008);
- the tokenizers that cut chunks in the index profile ([ADR-0012](../adr/0012-the-tokenizers-that-cut-chunks.md));
- a time limit on every audit write;
- the decision on audit retention, export and cleanup ([ADR-0013](../adr/0013-how-audit-rows-are-kept-exported-and-removed.md)).

## Boundaries v0.2 keeps

These are the guarantees as they stand. v0.2 does not strengthen them, and no document may describe them as stronger:

- **Authorization applies per SQL statement.** A search does not read one snapshot. A row comes from a statement that admitted it when it
  ran (ADR-0011).
- **Revocation is not retroactive for requests already running.** It reaches every retrieval statement that starts after it commits.
  Evidence already retrieved, or already sent to a chat model, stays with that request.
- **A citation is a snapshot.** The response carries the evidence text. `key@version` is not resolvable later, and no historical read is
  planned.
- **Audit fails closed and is kept** until an operator configures retention under ADR-0013.
- **No runtime dependency on Domain Driven Kit** (Q9). Conventions may be shared; code and artifacts are not.
- **Scope.** No knowledge graphs, agents, extra vector stores, Kubernetes or cloud providers (AGENTS.md, rule 8).

## Why data comes before optimization

Every retrieval number published so far comes from a corpus that cannot separate the changes v0.2 might want to make:

| What exists | Measured value | What it means for v0.2 |
|---|---|---|
| Corpus | 35 documents, 328 chunks as listed ([metrics-v2](../../benchmarks/reports/metrics-v2/report.md)) | Under load, dense latency goes to the embedding queue, not to PostgreSQL. No index structure can be shown to matter at this size. |
| Test split | 70 answerable cases; one case moves Recall by about 1.4 points ([dataset card](../../data/eval/DATASET_CARD.md)) | Paired intervals on ΔMRR@10 are about ±0.05 to ±0.09 wide. Smaller tuning effects are not findings. |
| Recall@10 | 0.94 to 0.99 for every strategy | Recall has no headroom left. Only ranking metrics can still move. |
| Long documents | No section in the demo corpus exceeds 120 words, and release 4 produces the same chunks as release 3 ([changelog](../../CHANGELOG.md)) | Long-input splitting is tested, but its effect on retrieval has never been measured. |
| Load | 35 documents on one laptop with other work running ([load smoke](../../benchmarks/reports/m4-load-smoke/report.md)) | The report says itself that it "says nothing about retrieval at scale". The bottleneck seen is the model service, not PostgreSQL. |
| Negatives | 31 authorization negatives, 32 cases with hard negatives, 35 that must find nothing | Enough for a security gate. Too few to report a false-positive rate per rule or per tag with useful intervals. |

**Consequence for the architecture.** The data in this repository does not support any of the following:

- **A second retrieval backend** (Q12). Its first premise is a PostgreSQL baseline measured at a larger scale, and there is none. The
  backend capability contract stays a precondition.
- **An approximate vector index** (ADR-0002). Filtered recall against exact search has not been measured.
- **Partitioning**, of chunks or of audit tables.
- **Index generations** (Q15). Reloading the demo corpus takes seconds, and no deployment has asked for a rebuild without downtime.

The plan therefore builds the evidence first. It keeps each of these as a question with a stated condition for reopening it.

## Work, in order

### 1. Evaluation data

**1a. Corpus scale.**

- **Fictional documents.** Grow the corpus to at least 300 fictional documents across the two tenants. Include long documents that
  release 4 has to split: sections over 400 words, code blocks, tables and space-free runs. Include more documents with a version history.
- **Distractor volume.** Add a generated set of plausible fictional distractor documents, labelled as such, so that candidate pools reach
  at least 10,000 chunks. Distractors carry labels like any document. They are never used as evidence. The dataset card states how they
  were generated and how they were checked.
- **Exit.** `ga-eval validate` passes, the dataset card lists every count, and a new dataset version is recorded. Earlier reports stay as
  they are, and their numbers are not compared across versions.

**1b. Cases and negatives.**

- **Answerable cases.** At least 200 answerable `test` cases, so that one case moves Recall by about half a point. The `dev` split grows
  in proportion and stays the only split used for tuning.
- **Negatives.** At least 60 authorization negatives, spread over clearance, department, project, version and cross-tenant. More
  same-tenant hard negatives, near-duplicate versions, and no-answer cases on topics the corpus nearly covers.
- **Label checks.** Evidence spans that fall inside long documents and cross a split point, so that evidence coverage (EC@k) measures
  what splitting does. Labels are reviewed by hand. The validator's overlap bands and per-tag balance apply as today.
- **Exit.** A committed baseline run on the new dataset, for every strategy, with a manifest version 2 that shows no drift.

**1c. Load evaluation.**

- **What is run.** A committed load report on the new corpus, measured on the CI runner class and named by its manifest:
  - concurrency sweeps per strategy;
  - per-channel SQL latency at about 1×, 10× and 100× the corpus;
  - connection-pool wait;
  - model-service queue time per lane.
- **Audit tables.** It also measures the audit write rate and how much the audit tables grow per 1,000 searches.
- **A query-plan check.** It includes the selective-filter benchmark that ADR-0002 deferred: exact search against HNSW for a project
  that owns about 2% of the chunks. This is a measurement, not an adoption.
- **Gates.** Every result is checked against the caller's visible set, as `./scripts/load-smoke` does now.
- **Exit.** The report says where the first bottleneck is at each size, with the evidence for it.

### 2. Operations that the plan already decided

- **Audit export** (ADR-0013, item 1). Delivered. The `audit_export` table, an export command that reads one snapshot, and a test that the
  manifest matches the files.
- **Audit retention and cleanup** (ADR-0013, item 2). Delivered. Opt-in retention per table with a one-day floor, deletion only of exported rows,
  bounded batches outside the request path, and an `audit.purge` event.
- **Storage gauges** (ADR-0013, item 3). Delivered. Two gauges and a dashboard panel. Retention numbers are not chosen for operators.

These items do not depend on step 1 and can run in parallel with it.

### 3. Retrieval optimization, only on the new evidence

- **What may change, and how.** Each change is tuned on `dev` and reported on `test` with paired intervals and its eval impact (rule 7):
  - candidates per channel, the RRF constant, and the rerank depth;
  - chunk size and overlap on the long documents;
  - heading context.
- **Rejection rule.** A change whose interval includes zero is not adopted as an improvement. It may still be adopted for another
  stated reason, as heading context was.
- **Index structure.** An approximate index or partitioning is considered only if step 1c shows exact search or a full scan as the
  bottleneck. It then needs an ADR with the filtered-recall measurement.

## Deferred, with the condition for reopening

| Item | Condition | Reference |
|---|---|---|
| Second retrieval backend | A measured PostgreSQL baseline at scale shows a limit that a backend would remove, and a capability contract exists in which the predicate is pushed into the query and fails closed | Q12 |
| Index generations (rebuild next to the live index) | A deployment needs a profile change without downtime, or the larger corpus makes a reload take long enough to matter | Q15, ADR-0007 |
| One read snapshot per search; stronger in-flight revocation | A use case requires it. Both need their own design: a read transaction that never spans a model call; a permission epoch, cancelling model calls, and a rule for answers built from revoked evidence | ADR-0011 |
| Historical citation reads | Not planned. It would need retained text, stable locators, and authorization against current labels | ADR-0011 |
| OIDC instead of demo tokens | The first real pilot | Q7 |
| Tamper-evident audit | Infrastructure for append-only storage or shipping events off the database | threat model, R6 |
| A statement-level faithfulness check for answers | A labelled answer set large enough to measure it | M3 analysis |

## Exit criteria for v0.2

- **Data.** Dataset and load reports from step 1 are committed. Every README number comes from a committed or released result file.
- **Operations.** ADR-0013 items 1–3 are delivered, or are explicitly moved to a later release, with the reason in the changelog.
- **Gates.** The CI gates still pass on the new dataset: security (exit 2), scope (exit 3), keyword rankings (exit 4), and the load smoke.
- **Limitations.** The known limitations are rewritten for the new scale, including what the new numbers still do not show.
- **Upgrade notes.** They state every schema and configuration change since v0.1.0, and the steps to move an existing database.
